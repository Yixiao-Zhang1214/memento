# Memento 先成稿后调风格流程设计

> 日期：2026-07-28  
> 状态：已确认设计，待书面规格复核  
> 范围：`memento-memory-editor` 纯文字 Skill

## 1. 问题

当前流程在追问结束后先要求用户选择正文风格，用户尚未看到整合效果，
难以判断是否需要调整。`style` 又默认设为 `truthful`，协议没有区分
“基础成稿”和“风格改写”两个阶段。

告白花案例还暴露出两个问题：

- 在事件、人物和意义已经充分时，系统追问了后续动作，却遗漏了更有
  馆藏价值的时间坐标；
- “来源”藏在正文结构里，过长、说明性太强，缺少独立且简短的表达。

## 2. 已确认的产品流程

采用“先成稿，后调整”的单向流程：

1. 接收图片、原始文字或语音。
2. 系统展示一个可跳过的追问。
3. 用户回答、换题一次或选择“就这样收藏”。
4. 系统整合所有输入，直接生成一版默认润色稿。
5. 同时生成标题、来源、摘要、正文和馆员评语。
6. 在成稿下方提供：
   - `就这样收藏`
   - `调整风格`
   - `自定义风格`
7. 用户没有调整意愿时，基础成稿就是最终稿。
8. 用户调整正文风格后，不重新追问事实。

正文风格不再是首次生成前的必选项。

## 3. 默认润色稿

第一版使用 `default_polish`，不是预设文学风格。

允许：

- 合并原始文字、语音和追问回答；
- 按真实事件顺序重排；
- 删除重复、口头填充和转写噪音；
- 补充必要连接词；
- 保留有价值的原话、对话、人称和语气；
- 生成一版可以直接收藏的完整文本。

禁止：

- 新增人物、地点、天气、日期、动作或心理；
- 把普通表达主动改成展签、散文、冷幽默或档案口吻；
- 因追求完整而补写用户没有提供的情绪和意义。

基础稿默认 120–260 个中文字；素材较少时可以更短。

## 4. 时间追问

新增问题意图 `time_probe`。

### 4.1 优先条件

当以下条件同时成立时，`time_probe` 优先于场景、动作和意义问题：

- E1 明确描述了一次可识别的单次事件；
- 事件时间没有出现在 E1 或 E3；
- 时间能改善“来源”、标题或纪念定位；
- 用户没有明确拒绝回答。

告白、毕业、离职、第一次见面、生日、旅行、收到礼物等事件通常适用。

### 4.2 问法

默认问题：

> 你还记得这大概是什么时候吗？

接受以下任一粒度：

- 具体日期；
- 年月或季节；
- “去年春天”“大学时”“刚工作那年”等人生阶段；
- 用户明确表示记不清。

不强迫用户提供精确日期。用户跳过或记不清时，不猜测时间。

### 4.3 降级

- E3 已有可靠时间：不重复询问。
- 事件持续多年、时间对纪念无帮助：改问场景、反差或意义。
- 沉重或防御输入：仍可问模糊时间，但必须保留明显的跳过动作。

## 5. 独立“来源”字段

在 composed memory 中新增必需字段 `source_line`。它是纪念文本的短来历，
不等同于事实说明，也不写进 `story_text`。

规则：

- 建议 4–18 个中文字；
- 优先使用“时间 + 人物 + 事件”，其中人物必须来自 E1；
- 时间缺失时，仍优先保留人物，再从用户原话、关键动作或物件与事件
  的关系中提取；
- 人物缺失时使用物件或事件本身，不猜测关系；
- 可以有轻微艺术感，但必须能够绑定到 E1/E3；
- 不使用完整说明句，不重复标题，不虚构日期或情绪；
- 正文风格调整不改变 `source_line`，除非用户明确要求修改来源。

示例：

| 证据 | `source_line` |
|---|---|
| 2024 年春天，男朋友告白时送花 | `2024年春，他的告白` |
| 男朋友告白时送花，但没有时间 | `他的一句“愿不愿意”` |
| 第一份工作时使用的杯子 | `第一份工作，那些夜晚` |
| 只有一张花束照片 | `镜头里的一束花` |

避免：

- `男朋友在告白那天送给我的一束花`
- `一段珍贵而浪漫的爱情回忆`
- `某年春天`（用户没有提供年份或季节）

## 6. 成稿后的风格调整

基础稿生成后返回三个动作：

```json
[
  {"id": "keep_draft", "label": "就这样收藏"},
  {"id": "adjust_style", "label": "调整风格"},
  {"id": "custom_style", "label": "自定义风格"}
]
```

### 6.1 预设风格

用户选择 `调整风格` 后，再展示：

- `truthful`
- `private_label`
- `light_poetic`
- `dry_humor`
- `fantasy_archive`

预设只改写 `story_text`，不新增事实，不改变 `source_line`，也不决定馆员
路由。

### 6.2 自定义风格

用户选择 `自定义风格` 后，可以用自然语言描述，例如：

- “更像我平时发朋友圈的语气”
- “写成三句话，克制一点”
- “保留口语，但再有画面一些”
- “参考某位作者的朴素和冷静”

系统将要求转换为 `style_features`、长度和结构约束，再生成原创改写。
涉及具体创作者时，只提取高级特征，不复制标志性句式或段落，不声称
模仿。

自定义风格是编辑指令，不消耗事实追问预算。

## 7. 馆员评语

馆员评语在基础成稿阶段生成，继续由系统根据内容选择情绪路由。

- 馆员不跟随预设或自定义正文风格；
- 正文改写后重新检查馆员评语是否与正文重复；
- 没有事实变化时，馆员路由保持不变；
- 内部参考人物仍不得出现在公共输出中。

## 8. 协议状态

输入新增：

```json
{
  "draft_state": {
    "base_draft_generated": false,
    "revision_state": "not_started",
    "selected_preset": null,
    "custom_style_request": null
  }
}
```

基础成稿输出：

```json
{
  "status": "needs_user_input",
  "mode": "compose_memory",
  "draft_stage": "base_polished",
  "source_line": "",
  "title": "",
  "summary": "",
  "story_text": "",
  "curator_note": "",
  "post_draft_actions": []
}
```

状态值：

- `draft_stage`: `base_polished`, `restyled`
- `revision_state`: `not_started`, `awaiting_direction`, `finalized`

用户选择 `keep_draft` 后返回 `status: complete`。完成预设或自定义风格改写
后，再次返回三个成稿动作，允许继续调整或收藏。

## 9. 错误与边界

- 用户不回答追问：从现有证据生成基础稿。
- 用户记不清时间：不再次追问，`source_line` 使用无时间写法。
- 自定义要求需要未知事实：缩小改写范围，不重新开启事实追问。
- 自定义要求与沉重情绪冲突：情绪安全优先，拒绝强行幽默或轻浮处理。
- 自定义要求为空：返回可恢复的 `EMPTY_CUSTOM_STYLE_REQUEST`。
- `source_line` 无法绑定证据：改写为物件优先的中性表达。

## 10. 测试

### 10.1 告白花主案例

输入：

> 图片：一束花  
> 这是男朋友告白那天送的花，我还记得他问我，愿不愿意做我女朋友，
> 我说好，我们就这么在一起了。

预期：

1. 第一问使用 `time_probe`：
   `你还记得这大概是什么时候吗？`
2. 不优先询问告白后的动作。
3. 用户回答或跳过后直接生成默认润色稿。
4. 不在生成前要求选择正文风格。
5. 有时间时来源类似 `2024年春，他的告白`；无时间时类似
   `他的一句“愿不愿意”`，人物不能被省略。
6. 成稿后出现收藏、预设风格和自定义风格入口。
7. 馆员路由为 `first_heartbeat`，公共输出不出现内部人物姓名。

### 10.2 其他案例

- E3 已有拍摄时间：不得重复询问时间。
- 多年使用的旧物：时间无明显价值时选择其他问题。
- 用户跳过：直接生成基础稿。
- 自定义“更短、更像朋友圈”：保留事实并按要求改写。
- 自定义点名作者：仅输出一般 `style_features`。
- 私人展签风格：正文可以展签化，`source_line` 仍保持短而独立。
- 无时间证据：不得在来源中生成日期或季节。

## 11. 验收标准

- 新记忆仍只展示一个可跳过的事实追问；
- 单次事件缺时间时，稳定优先 `time_probe`；
- 追问结束后先生成默认润色稿；
- 生成前不要求用户选择风格；
- 每个成稿都包含合法 `source_line`；
- E1 有人物时，`source_line` 优先保留人物；
- 成稿后同时支持预设与自然语言自定义风格；
- 正文风格不改变事实、来源或馆员情绪路由；
- 合法输出通过确定性校验；
- 告白花案例端到端测试符合本规格。
