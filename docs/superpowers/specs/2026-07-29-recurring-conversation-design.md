# Memento 循环对话与持续补充设计

日期：2026-07-29

## 目标

让默认成稿页成为记忆整理过程中的中途站，而不是强制终点。用户可以：

1. 主动补充一段新内容；
2. 主动让馆员再问一个问题；
3. 回到使用全部历史内容重新生成的默认成稿；
4. 无限重复以上循环，直到选择“就这样收藏”。

“无限”表示产品不设置对话轮数上限。HTML 验证版仍受单条输入、单次请求和浏览器会话内存限制，不承诺刷新页面后保留历史。

## 已确认的产品原则

- 首次流程保持不变：输入记忆 → 一个可跳过的追问 → 默认成稿。
- 每次继续对话都复用首次流程的节奏：一轮只出现一个问题，用户可回答、换题一次或跳过。
- AI 的主要角色是提问和引导用户多说，不发表长篇评论。
- 用户主动开启下一轮，因此不违反“每轮最多一个系统追问”的约束。
- 每轮完成后返回默认成稿页，用户可以再次开启新一轮。
- 所有用户输入必须累积使用，不能只使用最新一轮。
- 新证据加入后回到默认润色；之前选择的正文风格不自动沿用。

## 草稿页交互

正文卡片下方先展示一个继续对话区域：

- 标题：`还想再说一点？`
- 主操作一：`继续补充`
- 主操作二：`再问我一个问题`

其后依次展示：

1. `就这样收藏`
2. `调整风格`
3. `自定义风格`

继续对话入口放在收藏按钮之前，避免高强调度的收藏按钮过早截断讲述。

### 继续补充

点击后进入独立补充页：

- 标题：`再补充一点`
- 文本框标签：`还有什么想放进这段记忆？`
- 提交按钮：`写入并继续聊`
- 返回按钮：返回当前草稿，不改变草稿或历史

提交后先把文字追加为新的用户证据，再生成本轮唯一问题。

### 再问我一个问题

点击后直接开启新一轮问题，不预先增加用户证据。AI 使用全部历史用户内容、历史问题和当前草稿，选择一个未被问过、能增加正文信息的问题。

### 问题页

问题页沿用现有结构：

- 一个自然问题；
- 一个回答输入框；
- `换一个问题`，每轮限用一次；
- `先这样更新`，跳过本轮问题并回到更新后的默认成稿。

回答后立即关闭本轮问题预算，并使用全部历史证据重新生成默认成稿。问题本身不是事实证据，只有用户的输入和回答进入正文证据。

## 状态模型

前端新增两个核心状态：

### `conversationHistory`

按发生顺序保存对话项目：

```json
[
  {
    "id": "entry-1",
    "round": 0,
    "role": "user",
    "kind": "initial",
    "content": "首次输入"
  },
  {
    "id": "entry-2",
    "round": 0,
    "role": "assistant",
    "kind": "question",
    "content": "首次问题"
  },
  {
    "id": "entry-3",
    "round": 0,
    "role": "user",
    "kind": "answer",
    "content": "首次回答"
  }
]
```

允许的 `kind`：

- `initial`
- `supplement`
- `question`
- `answer`

只有 `role: user` 的项目转换为 E1 证据。`role: assistant` 的问题只用于避免重复和理解上下文。

### `conversationRound`

保存当前轮次：

```json
{
  "index": 1,
  "trigger": "supplement",
  "asked": true,
  "replaced": false,
  "answered": false,
  "closed": false,
  "previous_intent": "scene_probe"
}
```

允许的 `trigger`：

- `initial`
- `supplement`
- `ask_more`

每次从草稿页开启新一轮时：

1. `index` 加一；
2. 重置 `asked`、`replaced`、`answered`、`closed`；
3. 保留完整 `conversationHistory`；
4. 不把当前润色正文反向当作用户事实。

## API 契约

在现有 1.1 契约中增加可选字段，保持旧调用兼容：

```json
{
  "conversation_history": [],
  "conversation_round": {
    "index": 0,
    "trigger": "initial"
  }
}
```

规范化规则：

- 单条历史内容最长 5,000 字；
- 只接受已知的 `role` 和 `kind`；
- 历史顺序由数组顺序决定，不接受客户端提供的事实优先级；
- 重复提交同一个 `id` 时只保留一份；
- 首次旧版调用没有 `conversation_history` 时，继续从 `raw_text`、`transcript_text` 和 `follow_up_answer` 构建证据。

## 服务端流程

### 开启问题

`ask_followup` 接收完整历史与本轮状态：

1. 汇总全部用户证据；
2. 读取历史问题，排除已问过或语义高度相近的问题；
3. 找到当前正文最值得补充的一处人物、事件、关系或感受；
4. 返回一个易回答、可进入正文的问题；
5. 模型不可用或问题不合格时返回本地安全问题，不中断流程。

### 重新成稿

`compose_memory`：

1. 将全部 `role: user` 历史项目转换为独立 E1；
2. 复用首次提取的图片事实；
3. 重新生成标题、来源、摘要、正文和馆员评语；
4. 检查每轮用户内容是否被正文或其他成稿字段覆盖；
5. 不满足覆盖率、出现新增事实或模型不可用时，使用保守整合；
6. 返回 `base_polished`，清除之前的风格选择。

## 问题质量规则

每轮问题必须：

- 只提出一个信息请求；
- 能让简短回答进入正文；
- 不重复任何历史问题或已知答案；
- 不停留在图片或物品细节，除非它本身就是记忆目标；
- 优先补充人物、事件、关系、具体动作或用户已经暗示的感受；
- 跟随用户当轮语气；
- 允许用户跳过。

无限轮次不等于无限追问同一角度。若没有新的高价值方向，本地安全问题应邀请用户补充当前最想留下的事情，而不是重复时间、原因或物品属性。

## 异常与恢复

- 补充文字提交失败：保留输入框内容和当前草稿，允许原地重试。
- 问题生成失败：使用本地安全问题。
- 两个文字模型都失败：使用全部用户历史生成保守草稿。
- 图片模型失败：复用已有图片事实；首次失败时只保留“用户上传了一张图片”的安全元数据。
- 用户返回或取消：不追加尚未提交的内容。
- 重复点击提交：前端忙碌态禁用控件；服务端根据历史项目 `id` 去重。
- 页面刷新：HTML 验证版清空会话；持久化留给正式小程序。

## 验收标准

1. 首次成稿后可看到“继续补充”和“再问我一个问题”。
2. 主动补充后，补充内容先进入历史，再出现一个新问题。
3. 用户回答或跳过后回到更新后的默认成稿。
4. 连续完成至少十轮，不丢失任何已提交的用户内容。
5. 每轮只显示一个问题，并允许换题一次。
6. 新问题不与历史问题重复或高度相似。
7. 从风格改写稿继续补充后，结果回到默认润色。
8. 返回或取消补充不会改变现有草稿。
9. 图片只在首次上传时识别，后续轮次不重复发送图片。
10. 视觉、主文字和备用文字模型全部限流时，流程仍可继续。
11. 用户最终选择“就这样收藏”后进入文字定稿页。

## 测试范围

- 状态单测：轮次重置、历史追加、历史去重、取消不提交。
- 服务单测：多轮 E1 构建、问题去重、十轮内容覆盖、模型全失败。
- 浏览器验收：
  - 首次输入 → 回答 → 草稿；
  - 继续补充 → 回答 → 更新草稿；
  - 再问一个问题 → 跳过 → 更新草稿；
  - 调整风格 → 继续补充 → 默认润色；
  - 十轮循环后收藏。
